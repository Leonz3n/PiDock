# 外部编辑器的写入不参与 PiDock 写协调（明确豁免）

Status: accepted (2026-10-19; #108, #117 第 6 项 / 业主定 A)

#108 提出的是一个**设计问题**，不是已确认缺陷：外部编辑器由用户显式启动为 detached 进程（`host/open-editor.ts`、`main/external-editor.ts`），这条路径上不获取任何任务写声明；于是「编辑器正在写文件时 PiDock 也在写」这件事既没被禁止，也没被说明是哪一种口径。业主在 #117 定 **6A**：**明确豁免**并写进界面与文档。

## 决策

1. **编辑器是用户自己的工具，PiDock 不去 fence 它。** 外部编辑器进程的写入**不受** PiDock 写协调（`write-coordination.ts` / `path-coordination.ts`）约束；PiDock 不声称能阻止、串行化或撤销这些写入。
2. **PiDock 也不为编辑器让路。** 编辑器开着期间，PiDock **不暂停**自己的写入（提交收尾、清理、服务准备、任务创建收尾等）。这里没有「外部编辑中」状态、没有 mtime 探测、没有手动「结束编辑」、也没有超时判定——**因为不需要**：判定编辑器何时结束既不可靠（detached 进程无法可靠感知退出），也不该成为 PiDock 写入的前置条件。
3. **PiDock 只保证自己不并发写自己的记录。** 任务写声明（`write-coordination.ts`）管的是 **PiDock 自己的写入方之间**的先后，语义不变；跨任务共享真实路径的协调归 #11（见 ADR 0003），同样不包含编辑器。
4. **冲突的后果由用户承担并被说出。** 如果用户在编辑器里改文件、同时让 Agent 改同一处，两者都会落盘，由 Git 与用户判断成败；PiDock **不会**把这种情况报告为「写协调已保护你」。

## 交付位置（文案随事实走）

- 启动处（文件面板按钮下方，`DesktopToolDock`，`data-testid="dock-editor-coordination"`）：
  「外部编辑器对文件的写入不受 PiDock 写协调约束；它开着期间 PiDock 不会暂停自己的写入」
- 启动回执（Host `open-editor.ts` 的 `note`，常量在 `main/external-editor.ts` 的 `EDITOR_WRITE_COORDINATION_BOUNDARY`）：
  「编辑器对文件的写入不受 PiDock 写协调约束，PiDock 不会因为它开着而暂停自己的写入」

两处都有测试钉住（`desktopExternalEditor.test.tsx`、`open-editor.test.ts`），所以这句话不能被悄悄改回「已隔离」或「已协调」。

## Considered Options

- **让 PiDock 在编辑器打开期间持有写声明、自己的写入方避让**（#108 选项 1）：需要可靠判定「编辑结束」，而 detached 编辑器退出不可观测；用 mtime 猜测会把用户的长时间思考误判成编辑结束，或用超时把真实编辑期截断。代价是引入一个**看起来**像保护、实际靠猜的状态，比不保护更糟。不采用。
- **明确豁免并写进界面/文档**（#108 选项 2，采用）：与既有事实一致（当前代码就是这样），把「未定义」变成「有意为之」，代价是用户必须自己避免编辑器与 Agent 同时改同一处。
- **按文件 mtime 判断编辑结束**（#108 选项 3 的一种）：不可靠且会与其他写入方（Agent 自己的编辑）混淆。不采用。

## Consequences

- **不再有「外部编辑中」这个状态**；任何界面文案不得暗示 PiDock 会因编辑器而暂停或排队。
- 编辑器写入与 Agent 写入并发落盘时，PiDock 的写声明**不**报错——因为它本来就没参与。任务写声明只覆盖 PiDock 自己的写入方。
- 若未来要做「编辑器在场提示」，必须先解决「编辑结束如何可靠判定」，并作为新决策记录；在此之前不做。
- 本决策不新增任何拦截、状态或 IPC 字段；只把已有事实写成可核的一句话。
